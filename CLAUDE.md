# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-file client-side web app (`index.html`, ~4400 lines) for a photography business owner (Karin) to manage projects, clients, billing, and a daily task/calendar workflow. Hebrew UI, RTL. No build step, no package manager, no test suite — it's a static HTML file deployed as-is.

`karin-manager-template.html` in the repo root is an old unrelated draft (different color scheme/title) — not part of the live app, don't treat it as a reference.

## Commands

There is no build/lint/test tooling. In practice:

- **Preview locally**: open `index.html` directly in a browser, or serve it (`python3 -m http.server`) if testing anything that needs a proper origin (e.g. `fetch` calls).
- **Syntax-check after editing**: there's no linter, so the working pattern is to extract the main `<script>` block (the one starting after `/* ===== Firebase Sync ===== */` around line 1000) to a temp file and run `node --check path/to/script.js` to catch syntax errors before reloading in the browser.
- **Deploy**: push to `main` — GitHub Pages serves straight from the repo root at `https://karinrav-web.github.io/karin-manager/`. A Vercel deployment also auto-deploys on push but is not the one Karin actually uses.
- The repo **must stay public** — GitHub Pages on this account requires it, and flipping to private silently disables Pages (re-enabling requires manually reselecting the branch under Settings → Pages, it doesn't resume on its own).

## Architecture

Everything lives in one `<script>` block in `index.html`. Structure, in order:

1. **Firebase Sync** (`FB_CONFIG`, `fbSave()`) — Firebase Realtime Database, project `family-meds-c8900` (name is a legacy reuse, not a bug), data at path `karin-manager-data`. `fbSave()` debounces (800ms) and does a full `.set(state)` of the entire app state on every save — there is no partial/field-level write.
   - **Critical gotcha**: Firebase's `.set()` throws *synchronously* if any property anywhere in the object is `undefined` (not a rejected promise — it never reaches `.catch()`). Because saves are whole-state, one bad field (e.g. a project missing `adjItems`) silently kills syncing for *everything*, not just that record. This is why saves go through `JSON.parse(JSON.stringify(state))` first — that strips stray `undefined` keys. Any new `.set()` call site must do the same round-trip.
   - Auth is Firebase Anonymous Auth (`signInAnonymously()`), required by the DB rules (`auth != null` for read/write). This is access control against random internet traffic, not against someone with the PIN — see the password lock note below.
   - `startSessionWatch()` / `SESSION_PATH` is a lightweight "someone else has this open" heartbeat (separate sibling path from `FB_PATH`, so it isn't wiped by the full-state `.set()`). It's advisory only — it warns, it doesn't lock.

2. **Password Lock** — a PIN screen gate (`BOOTSTRAP_HASH`, `hashPin()`). This is enforced client-side only; it is not backed by Firebase rules, so it's a UX deterrent, not real access control. (The DB rules just require *any* anonymous auth session, not a matching PIN.)

3. **App** (`state`, `load()`, `save()`, `render()`) — the core data/render loop.
   - `state = {projects, tasks, settings, editDays, lastReset, billing, credits, clients}` is the single in-memory source of truth.
   - `load()` reads `localStorage` (`karin_pm` key) first for instant render, then signs in to Firebase and attaches a `.on('value', ...)` listener; `mergeCloudState()` reconciles cloud vs. local. `_fbInitialized` guards against saving stale local data over Firebase before the first cloud snapshot arrives.
   - `save()` persists to `localStorage` and also writes a same-day auto-backup under key `karin_ab_YYYY-MM-DD` (separate from the live key) — this is the recovery path if a sync bug ever wipes cloud data; restorable via the sidebar "🔄 שחזר גיבוי אוטומטי" button on the same browser/device.
   - `render()` is a manual full re-render dispatcher — it calls each page's `render*()` function directly (no framework, no virtual DOM, no reactivity). Any state mutation that should reach the screen needs an explicit call into the relevant `render*()`.
   - Page switching (`showPage()` / `showPageMobile()`, separate desktop/mobile nav) toggles `.page`/`.nav-item` classes and re-renders only the page being shown (`morning`, `projects`, `report`, `billing`). The `report` page is titled "לוח עבודה" in the UI and, as of 2026-09-22, bundles what used to be three separate pages/tabs: the daily metrics/goals report, the monthly editing-capacity work-plan grid (Gantt-style, `renderWorkPlan()`, projects × upcoming days with per-day photo counts in `p.dailyPlan`), and the edit/shoot-day calendar + capacity settings (`renderCalendar()`, formerly page `calendar`). There is no standalone `calendar` or `workplan` page anymore — don't assume the old CLAUDE.md description of a separate "לוח עריכה" tab still holds.
   - **Navigation restructure, phase 1 (2026-10-01)**: new `settings` page (`#page-settings`) now holds the editing-settings card (moved out of the report page — same `s-hours`/`s-rate`/`s-rate-proj`/work-day inputs, `loadSettings()` still finds them by id), the theme swatches (moved out of the morning customize bar), and the backup/restore/PIN/delete-all buttons (moved out of the sidebar bottom). The sidebar's `scheduler` item is now an external link to the scheduler app (the `#page-scheduler` div is unused). The billing page (UI title now "כספים") has in-page tabs: elements carry `data-btab="overview|records|clients|credits"` and `applyBillingTab()` (called at the top of `renderBillingPage()`) hides the others via `.btab-off`; `setClientFilter()` switches to the records tab. The duplicate-check card stays outside the tabs on purpose (it's a warning). Phase 2 (same day) added the project side panel (below). Phase 3 made the morning screen actionable: each row of `renderDailyFocus()` now has −/+1/+5 (→ `bumpEdited`), today's done/goal (or a one-click "יעד N?" that calls `updateGoalTarget` with the suggested allocation), and a timer toggle (→ `toggleTimer`). Rows worked on today or with a running timer stay listed even if the allocation skipped them. `renderProjects()` now also calls `renderDailyFocus()`, and both timer intervals update any `[data-timer="<id>"]` element besides `ptv-<id>`. Phase 4 (visual refresh) is a single CSS override block appended at the end of the main `<style>` ("Design refresh … phase 4"): darker default `--accent` (#b0532f) and `--text3`, rounded nav pills, no desktop topbar, larger page/card titles, metric cards without icon circles, panel drag handles only on hover, and `.main{min-width:0}` so the wide work-plan table scrolls inside `#wp-table-wrap` instead of stretching the whole page. Prefer editing that block over the original rules when adjusting the look. Phase 5: the side panel has its own tabbed layout (`if (inPanel) {…}` early return in `projectCardHtml`: header + stage row, tabs עריכה/כסף/הערות/לקוח via `setPanelTab()`/`panelTab`, stat tiles). The expanded-card markup is split into `_pp*` template consts (`_ppStages`, `_ppCtrl`, `_ppTimerEdit`, `_ppSessions`, `_ppQuick`, `_ppGoalBar`, `_ppSummary`, `_ppNotes`) shared by the in-list expanded card and the panel — change those pieces once and both update. The client pane is injected by `renderProjectPanel()` at the `<!--pp-client-->` marker.
   - **Project side panel** (`#proj-panel`, `openProjectPanel(id)` / `closeProjectPanel()` / `renderProjectPanel()`): the per-project card markup now lives in `projectCardHtml(p, _allFinish, inPanel)` (extracted from `renderProjects()`'s map). The panel renders the card fully expanded; the list renders that same project collapsed while the panel is open (`isPanelProject()`), because the expanded card carries element ids (`ptv-`, `ptb-`, `editedtoday-`, `timer-edit-`, `sedit-`…) that `getElementById`-based code (e.g. the timer tick) relies on being unique. `renderProjects()` calls `renderProjectPanel()` first, so every existing mutation path that re-renders the list also refreshes the panel. Entry points: project names on the morning focus/urgency lists, tasks (`goToProject`), work-plan rows, report rows, billing search results/records (`recProjHtml(r)`, only when the record's `projectId` resolves), client-card project rows, and clicking a card header in the projects list (the ▼ arrow still expands in place). Panel z-index is 89/90 — below `.modal-bg` (100/200) so edit/payment modals open on top of it.

4. **Billing / Revenue** (from ~line 1916) — the largest and most fragile section: client payments, VAT handling (`isCash` = no-VAT opt-in), supplier costs/payouts, per-project billing history, duplicate-record detection, monthly summaries and charts. Several past bugs here involved: billing rows merging across different projects that happen to share an id, double-VAT display on supplier lines, and auto-generated income records drifting out of sync with manually-edited payer amounts — when touching billing math, check whether a record is auto-generated vs. user-edited before assuming it's safe to recompute.

5. **Dashboard Customize** (from ~line 2716) — user-configurable dashboard widget layout/visibility, persisted in `state.settings`/localStorage.

## Other notable behavior

- **Deleted-ids tombstones for billing/credits (2026-10-01)**: `mergeBilling(local, cloud, deleted)` used to be a plain union by id, so any income record deleted on one device/tab (incl. un-ticking "שולם" in `togglePaid`, which deletes the auto record) came back on the next cloud merge; re-ticking then created a second record. That produced ~₪118K of phantom 2026 income (29 orphan duplicates). Now `state.deletedIds = {billing:[…], credits:[…]}` (string ids) is unioned across local/cloud in `mergeCloudState()` and filtered out of the merge; every deletion path calls `markDeleted(kind, ids)`. Any NEW place that removes a billing/credit record must call `markDeleted` too, or the record will resurrect. Older app versions still open on another device drop `deletedIds` when they save, but the union on the next new-version merge restores them. `findDuplicateAutoRecords()` / the banner on the כספים page (`#dup-cleanup-banner`, `cleanupDuplicateAutoRecords()`) removes auto records that are identical (same projectId + total + supplier names) to one a payer still references — never manual/CSV records, never a referenced record.

- **Print/PDF export**: functions build a full standalone HTML document as a template string (see the payment-breakdown export around line 3842) and open it in a new window with `window.onload=()=>window.print()` — there's no PDF library, it relies on the browser's print-to-PDF.
- **External integration**: `syncShootDates()` fetches shoot dates from a separate sibling project (`photo-scheduler-wine.vercel.app`) and auto-marks working days as edit days in the calendar. This is a one-way pull, not part of this repo.
- Data model helper functions to know about: `normalizeProject()` and `dedup()` (dedupe/repair projects and tasks on load), `applyDayReset()` (daily rollover logic), `recalcClientShare()` (per-project client billing recompute called at the top of every `render()`).
- **`p.goalDaily` is a mirror of `p.dailyPlan[todayStr()]`, not an independent field.** Any code that sets "today's goal" (the report page's יעד input, a project card, the edit modal, the work-plan grid's own today-column cell) must go through `setTodayGoal(p, v)` or replicate its dual write, or the two will drift apart. `applyDayReset()` doesn't zero `goalDaily` on a new day — it re-derives it from `dailyPlan[today]`, so a value planned ahead of time on the work-plan grid becomes "today's goal" automatically once that date arrives. `mergeCloudState()` derives it the same way from the merged `dailyPlan` — never merge `goalDaily` itself (e.g. `Math.max(local, cloud)`), that was the exact bug fixed 2026-09-22 where a stale local number outlived a day rollover because the max let it win and nothing re-derived it afterward.
- **There is no manual "new day" button** (removed 2026-09-22 — it used to unconditionally wipe `editedToday`/`goalDaily` on click, even when the day hadn't actually rolled over, silently discarding same-day progress). Day rollover is `applyDayReset()` alone, called automatically on every `load()`; it's idempotent (only fires once `state.lastReset !== todayStr()`). `todayStr()` treats the work day as starting at **2am, not midnight** — a late-night session between 00:00–01:59 still resolves to the previous calendar day, so don't reintroduce a raw `new Date()` for "today" anywhere that needs to agree with `editedToday`/`dailyPlan`/the report page's date display; derive it from `todayStr()` instead (see `renderWorkPlan()`'s `now` for the pattern).
- **`load()` persists its own `applyDayReset()` result to `localStorage` immediately** (2026-09-24) rather than leaving the reset in memory only — narrows the window where `mergeCloudState()`'s fresh `localStorage` read (it doesn't trust in-memory `state`) could see yesterday's un-reset data.
- **`p.editedTodayDate` is what actually makes `editedToday` trustworthy — not `state.lastReset`** (2026-09-24). Originally `applyDayReset()` reset every project's `editedToday` in one shot, gated by a single global `state.lastReset !== todayStr()` check — once that flag got stamped "today" (even wrongly, e.g. by a sync race), no project's `editedToday` was ever re-checked again until the next real calendar day, so a stale value could sit there uncorrected all day. Now every project carries its own `editedTodayDate`, and `applyDayReset()` checks/resets per-project on every `load()`/merge regardless of the global flag — self-healing even within the same day. `updateEditedToday()` and `bumpEdited()` both diff against 0 (not the raw stored value) whenever `editedTodayDate` isn't today, and stamp it when they write — skip either of these and a stuck stale value silently corrupts `p.edited` the next time someone "fixes" the display by typing 0 into it. `mergeCloudState()`'s `editedToday`/`goalDone` merge picks per-field based on which side's own `editedTodayDate` actually says today, never a blanket `Math.max(local, cloud)`.
